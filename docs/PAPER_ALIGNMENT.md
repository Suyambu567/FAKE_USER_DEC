# Aligning this project with *Fake Profile Detection Using XGBoost Algorithm*

Paper: Venkadesh, Khan, Ramkishore, Rakesh and Suyambulingaraj, ICRDICCT'25,
pages 663–670, DOI 10.5220/0013941400004919.

This records what the project already did, what the paper asks for, what changed,
and — the part that matters most — what the data will not support and was
therefore **not** implemented. Every number below was measured in this
repository. None is copied from the paper.

---

## 1. What the audit found

| # | Question | Answer before this work |
|---|---|---|
| 1 | How is data loaded? | `pd.read_csv` in `ml/train.py`. No loader module. |
| 2 | Which dataset? | `data/dataset.csv` (10k rows) and `data/synthetic_signal.csv` (50k, generated by `ml/generate_dataset.py`). |
| 3 | Input features | 8 raw numeric columns + `Bio Text`. **None** of the paper's profile attributes. |
| 4 | Missing values | `dropna` — rows deleted, never imputed. |
| 5 | Duplicates | **Not handled at all.** |
| 6 | Categorical encoding | None. `Language` was dropped entirely. |
| 7 | Normalisation | `StandardScaler` inside the pipeline. Correct. |
| 8 | Feature engineering | None in the shipped path. `ml/benchmark.py` had a `DerivedFeatures` class the trained model never used. |
| 9 | Textual features | TF-IDF over the bio, fitted inside the pipeline. Correct. |
| 10 | Behavioural features | Raw activity columns only; no ratios, no post frequency. |
| 11 | Algorithm | `RandomForestClassifier`. |
| 12 | XGBoost training | Only as one entry in `ml/benchmark.py`. Never trained, never saved, never served. |
| 13 | Class imbalance | `class_weight="balanced"` on the forest. Never measured; no oversampling. |
| 14 | Metrics | accuracy, baseline, lift, precision, recall, F1, ROC-AUC, CV. **No confusion matrix.** |
| 15 | Model saving | `joblib` + `model_meta.json`. Good — records the sklearn version and refuses to load on a mismatch. |
| 16 | API | FastAPI, already production-shaped: envelope responses, request IDs, rate limiting, API-key auth, bounded inference concurrency. |
| 17 | Real-time detection | Yes — `POST /api/v1/predict`, `/predict/batch`, `/lookup/{username}`. |
| 18 | How input reaches the model | Pydantic `ProfileFeatures` → `ModelService._to_frame` → the fitted pipeline. |
| 19 | Train/serve preprocessing | Shared, because the whole preprocessor is *inside* the pickled pipeline. No skew. |

**The headline finding was not in that table.** The two datasets are in a
stalemate:

* `data/dataset.csv` **has** the paper's profile columns (`Real Name`,
  `Profile Picture`, `Profile Link`) — and its labels are drawn by
  `np.random.choice` in `data/app.py:48`. Largest standardised mean difference
  between the classes across all numeric features: **0.0606**. There is nothing
  to learn.
* `data/synthetic_signal.csv` **has** real signal (max |SMD| 1.48) — and
  `ml/generate_dataset.py` never emitted the paper's profile columns, so the
  paper's Table 1 could not be trained at all.

So implementing the paper's feature set required extending the generator. That
is stated wherever the model is served, and the control experiment in §5 shows
exactly what the pipeline scores when the labels carry no information.

The three unavailable attributes are **not fabricated**. `ml/features.py`
contains the code to build all three the moment a `username` or `private` column
appears; until then `availability()` reports them as unavailable, the trainer
writes that into `model_meta.json`, and the API surfaces it on
`GET /api/v1/model/info`.

Beyond Table 1, section 4.2's "activity logs, post frequency" and NLP features:

* **behavioural** — `follows_per_follower`, `posts_per_year` (post frequency),
  `likes_per_follower`, `comments_per_like`, plus `verified`,
  `account_age_years`, `engagement_rate`, `avg_likes_per_post`,
  `avg_comments_per_post`, `engagement_consistency`.
* **textual** — TF-IDF(200) over the bio, plus `bio_is_empty`,
  `bio_word_count`, `bio_digit_ratio`, `bio_upper_ratio`, `bio_has_url`,
  `bio_promo_terms`.

26 engineered features in total on `data/paper_signal.csv`.

## 4. Class imbalance

Measured before anything is applied, and the decision is recorded:

| Dataset | negatives/positives | Strategy chosen | Why |
|---|---|---|---|
| `data/paper_signal.csv` | 1.73 | `class-weight` (`scale_pos_weight=1.7296`) | outside the 0.8–1.25 band |
| `data/dataset.csv` | 0.98 | `none` | already balanced; reweighting would only add variance |

`--imbalance oversample` implements the paper's other option (random minority
oversampling). It runs **after** `train_test_split` and touches only the
training split — duplicating rows first would put copies of the same profile on
both sides of the split and inflate every metric.

## 5. Measured results

### 5.1 The deployed model — `data/paper_signal.csv`, 50k rows

XGBoost, `scale_pos_weight=1.7296`, 400 trees, depth 6, lr 0.08. 40k train /
10k test, stratified.

| Metric | Value |
|---|---|
| Accuracy | **0.9409** |
| Majority-class baseline | 0.6337 |
| **Lift over baseline** | **+0.3072** |
| Precision (Fake) | 0.9349 |
| Recall (Fake) | 0.9014 |
| **F1 (Fake)** | **0.9179** |
| Specificity | 0.9637 |
| ROC-AUC | 0.9331 |
| PR-AUC | 0.9015 |
| CV accuracy (5-fold) | 0.9400 ± 0.0018 |

Confusion matrix (10,000 test profiles):

|  | predicted Real | predicted Fake |
|---|---|---|
| **actual Real** | 6,107 | 230 |
| **actual Fake** | 361 | 3,302 |

Top features by gain: `follows_per_follower` (0.242),
`ratio_numlen_fullname` (0.036), `posts` (0.035). The single strongest signal is
a behavioural ratio; the second is a paper Table 1 profile feature.

This lands in the paper's stated 90–95% band. That is a coincidence of
difficulty, not a reproduction: the paper's number comes from its own data, and
`--label-noise 0.06` in the generator is what caps this one.

### 5.2 Control — `data/dataset.csv`, random labels

The identical pipeline, same code path, on the dataset whose label is drawn by
`np.random.choice`:

| Metric | Value |
|---|---|
| Accuracy | 0.5110 |
| Baseline | 0.5045 |
| Lift | +0.0065 |
| F1 | 0.5173 |
| ROC-AUC | 0.5090 |
| CV accuracy | 0.5073 ± 0.0110 |

The quality gate fired on its own: *"Accuracy does not meaningfully exceed the
majority-class baseline. This model has learned nothing."* Kept at
`backend/artifacts/xgb_instagram_csv/` as the control.

**Read the two together.** §5.1 is not evidence that the pipeline detects fake
Instagram accounts. It is evidence that the pipeline recovers the structure that
exists in its input — and §5.2 is evidence that it does not invent structure
when there is none.

### 5.3 Algorithm comparison — is XGBoost actually best here?

The paper's Table 2 puts XGBoost at 90–95% and top of its field. Measured on
this project's data, on the same engineered features the API serves (10,000
rows, 3-fold stratified CV, `ml/benchmark.py --paper-features`):

| model | accuracy | ±std | ROC-AUC | F1 | fit s | artifact MB |
|---|---|---|---|---|---|---|
| Gradient Boosting | 0.9381 | 0.0048 | **0.9333** | 0.9149 | 7.59 | 0.15 |
| **XGBoost** | 0.9390 | 0.0036 | 0.9325 | 0.9163 | **0.89** | 0.51 |
| Random Forest | 0.9400 | 0.0041 | 0.9324 | 0.9176 | 0.77 | 2.91 |
| k-NN (k=25) | 0.9362 | 0.0042 | 0.9322 | 0.9120 | 0.06 | 1.12 |
| Extra Trees | 0.9400 | 0.0041 | 0.9320 | 0.9176 | 0.60 | 1.95 |
| MLP (128,64) | 0.9390 | 0.0043 | 0.9317 | 0.9161 | 0.96 | 0.58 |
| HistGradientBoosting | 0.9384 | 0.0042 | 0.9309 | 0.9154 | 1.52 | 0.39 |
| AdaBoost | 0.9344 | 0.0038 | 0.9304 | 0.9093 | 2.58 | 0.02 |
| Logistic Regression | 0.9400 | 0.0041 | 0.9304 | 0.9176 | 0.09 | 0.00 |
| Linear SVM | 0.9400 | 0.0041 | 0.9301 | 0.9176 | 0.13 | 0.00 |
| Gaussian Naive Bayes | 0.9396 | 0.0039 | 0.9295 | 0.9171 | 0.06 | 0.01 |
| Decision Tree (depth 8) | 0.9389 | 0.0040 | 0.9285 | 0.9160 | 0.17 | 0.01 |
| Baseline (majority class) | 0.6272 | 0.0001 | 0.5000 | 0.0000 | — | — |

**XGBoost is not the winner on this data.** It is sixth by accuracy and second
by ROC-AUC, and the whole field from Decision Tree upwards sits inside a
0.006 band — smaller than the fold-to-fold standard deviation of every row in
it. On this data those models are tied, not ranked. A plain Logistic Regression
matches the best accuracy at 0.09 s and a zero-megabyte artifact.

What the table does say clearly is that **the features carry the signal**: every
algorithm, including a depth-8 decision tree and a Gaussian Naive Bayes, gains
~0.31 over the baseline. That is a property of `ml/features.py`, not of the
booster.

XGBoost is what ships because it is the paper's algorithm and because it is the
best cost trade in the group — 0.89 s to fit, 0.51 MB on disk, 12.5 ms per
1,000 rows. Not because it scored highest. It did not.

LightGBM is in the candidate list but was skipped (`--skip LightGBM`): on this
80-core host it spends minutes in thread contention on data this small while
every other candidate finishes in seconds, and it is not one of the algorithms
the paper compares.

## 6. What was changed

| # | Change | Why | Paper stage | File |
|---|---|---|---|---|
| 1 | Shared feature module | One definition of every feature, used by training and by the API | Feature Engineering | `backend/ml/features.py` (new) |
| 2 | Cleaning module | Missing values imputed, duplicates removed, values recorded for reuse at inference | Pre-Processing | `backend/ml/preprocess.py` (new) |
| 3 | Evaluation module incl. confusion matrix | The paper names accuracy and F1; accuracy alone is not enough | Model Evaluation | `backend/ml/evaluation.py` (new) |
| 4 | XGBoost trainer | The paper's algorithm, end to end | XGBoost Model | `backend/ml/train_xgb.py` (new) |
| 5 | Generator emits Table 1 fields | The only dataset with signal had none of the paper's profile columns | Data Collection | `backend/ml/generate_dataset.py` |
| 6 | Figures 4 and 5 as SVG | Paper §5.1; no plotting dependency added | Visualization | `backend/ml/visualize.py` (new) |
| 7 | `--paper-features` on the benchmark | Compare algorithms on the features actually deployed, not a benchmark-only set | Results | `backend/ml/benchmark.py` |
| 8 | API serves the XGBoost artifact | Deployment stage | Deployment | `app/core/config.py`, `.env`, `.env.example` |
| 9 | `ModelService` uses `build_feature_frame` | Same function at fit time and request time — no training-serving skew | Deployment | `app/services/model_service.py` |
| 10 | Table 1 fields on the request schema | The paper's profile attributes have to be sendable | Real-Time Detection | `app/schemas/predict.py` |
| 11 | `imputed_fields` on the response | A prediction made from defaults must not look like one made from data | Real-Time Detection | `app/schemas/predict.py`, `app/api/v1/routes/predict.py` |
| 12 | `/features` derived from the schema | The hand-written list silently omitted the new fields | — | `app/api/v1/routes/analytics.py` |
| 13 | `DATASET_PATH=` no longer means `Path(".")` | Pre-existing bug: an `IsADirectoryError` traceback on every startup | — | `app/core/config.py`, `app/services/analytics_service.py` |

Not changed, deliberately: `ml/train.py` (the RandomForest the static `webapp/`
ships), `webapp/`, the envelope/auth/rate-limit/logging layers, and
`artifacts/web/`.

## 7. Final data flow

```
data/paper_signal.csv                      ml/generate_dataset.py
        |
        v
ml/preprocess.clean()                      impute -> dedupe -> validate target
        |                                  (records impute values in the artifact)
        v
ml/features.build_feature_frame()          Table 1 + behavioural + textual
        |
        v
train_test_split(stratify=y)               <-- imbalance handled only after here
        |
        v
ColumnTransformer                          StandardScaler | TF-IDF | OneHot
        |
        v
XGBClassifier(scale_pos_weight=...)
        |
        v
ml/evaluation.evaluate()                   + confusion matrix, + cross-val
        |
        v
artifacts/xgb/{model.joblib, model_meta.json}
        |
        v
app.services.ModelService.load()           version-checks sklearn AND xgboost
        |
POST /api/v1/predict
        |
        v
ProfileFeatures (pydantic)  ->  impute omitted optional fields from metadata
        |
        v
ml.features.build_feature_frame()          <-- THE SAME FUNCTION as training
        |
        v
pipeline.predict_proba()  ->  {label, confidence, probabilities, imputed_fields}
```

## 11. Limitations

1. **The model is trained on synthetic data.** It has learned
   `ml/generate_dataset.py`'s rules, which are modelled on how fake engagement
   behaves but are not measurements of it. Not fit to action real accounts.
2. **Three Table 1 attributes are unimplemented** — `private`,
   `ratio_numlen_username`, `sim_name_username` — because no dataset here has a
   username or a private flag. The code to build them exists and activates when
   the columns do.
3. **`Language` carries no signal by construction**; it is drawn identically for
   both classes. It exercises the categorical branch honestly rather than
   inflating accuracy.
4. **Omitted optional fields are imputed**, and the model never saw an absent
   name during training, so it extrapolates. `imputed_fields` says when this
   happened; supply the full profile for a prediction you intend to rely on.
5. **Bio text has 35 distinct values** in the generated data, so the TF-IDF
   branch is closer to a lookup than to language understanding.
6. **The paper's own accuracies are not reproduced or claimed.** Its Table 2
   ranges describe its data; §5 describes this data.
